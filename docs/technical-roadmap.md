# 赛博鱼缸：3D 技术框架与开发路线

> 文档类型：技术路线调研稿
> 调研日期：2026-11-13
> 状态：方案建议，需通过小型原型验证
> 项目定位：以虚拟鱼缸为核心的 3D 可交互建造与养成游戏。“赛博”指虚拟游戏鱼缸，不预设赛博朋克美术风格。

## 1. 结论摘要

项目按 3D 桌面游戏规划。首选候选技术栈为 **Unity 6.3 LTS + URP + C# + Blender**。先做一个技术原型，验证鱼缸水体观感、鱼的三维游动、相机观察和物件摆放，再确定是否进入完整制作。

Godot 4.7.2 是可行备选，具备 3D 场景导入、动画混合和三维导航能力。若团队熟悉 Godot，或更偏好轻量开源工具链，可以使用相同原型对比。当前不建议在未验证水体和鱼类表现前制作大量内容。

本方案修正了项目讨论稿 v0.1 中“首版先不做 3D”的旧前提；鱼缸的具体视觉风格仍需单独确定。

## 2. 推荐技术栈

| 层 | 推荐 | 作用 |
|---|---|---|
| 游戏引擎 | Unity 6.3 LTS | 3D 场景、灯光、材质、交互和桌面构建 |
| 渲染 | URP | 为桌面目标提供可配置的渲染管线，并保留画质档位空间 |
| 玩法逻辑 | C# | 生态模拟、鱼类行为、摆放交互和存档 |
| 3D 制作 | Blender | 鱼、鱼缸、设备、造景模型及骨骼动画 |
| 输入 | Unity Input System | 鼠标、键盘及后续手柄的统一操作映射 |
| 静态内容数据 | ScriptableObject | 鱼种、设备、造景等开发期配置资产 |
| 玩家进度 | 版本化 JSON 存档 DTO | 保存鱼缸布局、鱼只状态、设置和解锁内容 |
| 版本管理 | Git；大型二进制美术资源可配 Git LFS | 代码、场景和资源的版本追踪与协作 |

Unity 官方当前将 6.3 LTS 列为 LTS 版本，并说明支持至 2027 年 12 月。正式开工时应固定 Unity 编辑器和依赖包的具体版本，避免生产中途随意升级。

ScriptableObject 适合保存项目中的静态配置数据，但 Unity 文档指出，已发布的游戏不能依靠 ScriptableObject 保存玩家运行时进度。因此，玩家存档应使用单独的数据结构并序列化到用户数据目录。

## 3. 主要系统设计

### 3.1 场景与相机

首个场景只包含一个房间和一只鱼缸。鱼缸内部至少拆分为缸体/玻璃、背景、底床、造景、设备、鱼、水面和水体视觉层，避免把所有效果塞进单一材质。

桌面交互建议提供环绕观察、平移和缩放。点击鱼、设备或造景时，通过屏幕射线检测得到目标对象，再打开对应操作或信息面板。相机交互与摆放模式应分开，避免玩家拖动视角时误移动物件。

### 3.2 造景与设备摆放

建议流程：选择物件 → 显示半透明预览 → 吸附到网格或指定表面 → 检查占位、碰撞和摆放限制 → 确认。

物件数据至少需要包含稳定 ID、预制体引用、占用尺寸/形状、允许摆放表面、可旋转轴、价格或解锁条件。鱼缸保存布局时记录 ID、位置、旋转和必要的状态值，不保存场景对象引用。

### 3.3 鱼类移动与行为

鱼在缸内自由活动，活动区域是有边界的三维空间。不要直接把为地面行走设计的 NavMesh 当作水中鱼类的运动系统。首版可采用自定义转向与空间目标点：鱼在游动范围内选择目标点，平滑转向，远离缸壁和大型障碍，并在进食等事件下改变目标和速度。

首版行为建议控制为缓慢巡游、转向、避壁、觅食/响应喂食、短暂加速。后续再按鱼种加入群游、躲藏、争地盘等差异。群游可逐步加入邻近鱼只间的分离、聚合和方向协调，避免第一版就追求完整群体仿真。

鱼的网格和骨骼动画由 Blender 制作。可用尾部摆动动画表达游速，再由程序控制鱼体方向、速度和行为状态。Unity Animator 状态机适合组织离散行为动画；运动和转弯仍由游戏逻辑驱动。

### 3.4 水体与玻璃表现

第一版采用实时渲染的近似效果，不做真实流体模拟：水面网格、定制材质/着色器、光照、气泡粒子、轻微折射或水下雾化。水体、玻璃和鱼的透明排序与可见性需要尽早实测，因为这些效果会显著影响观感和帧率。

建议先用简单几何和一条临时鱼模型完成“空缸 + 水面 + 一条鱼”画面原型。只有达到目标画面后，才批量制作正式鱼种和房间资产。

### 3.5 生态模拟与表现分层

将模拟状态与 3D 视觉对象分离：C# 逻辑维护水质、过滤成熟度、温度、鱼只饥饿/压力/健康等状态；场景对象读取这些状态并呈现鱼的行为、粒子、颜色或 UI 提示。

模拟采用固定步长更新，不与每帧渲染绑定。首版只选择少量可以解释且相互影响的指标；玩家应能从检测结果或提示理解变化原因，而不是只看到抽象惩罚。

### 3.6 数据与存档

静态定义与玩家实例分开：

- 静态定义：鱼种需求、设备参数、造景信息、模型/材质引用，放在开发期数据资产中。
- 玩家实例：某条鱼的状态、某件设备的位置、当前水质、鱼缸布局和进度，放在运行时模型中。
- 存档：保存静态定义 ID 和玩家实例状态，包含 `save_version`；加载时校验缺失 ID 并支持后续迁移。

首版 JSON 便于调试和检查；存档中保存稳定 ID 与简单数值/向量，不直接序列化引擎对象。若未来数据量或存储需求变大，再评估二进制格式。

## 4. 开发阶段与验收重点

### 阶段 A：3D 技术原型

内容：一个简化缸体、一种临时鱼模型、水面和基础灯光；相机环绕/缩放；鱼能在缸内平滑巡游并避开缸壁。

验收重点：鱼、水面、玻璃的画面关系可接受；相机操作舒服；鱼不会穿出鱼缸或明显抖动；原型在目标电脑上运行稳定。

### 阶段 B：布置交互切片

内容：添加少量底床/造景/设备；完成选取、预览、旋转、吸附、放置和撤销；保存并加载一次布局。

验收重点：玩家能清楚知道物件放置是否有效；遮挡和误选可控；重新打开游戏后布局正确恢复。

### 阶段 C：核心养成循环

内容：加入少量鱼种、喂食、简化水质变化、检测和可解释的状态反馈；支持暂停、加速和基础时间推进。

验收重点：布置、放鱼、观察、维护形成闭环；行为能反映环境变化；管理负担符合轻松养成的定位。

### 阶段 D：内容扩展与发布准备

在原型反馈稳定后，再扩展鱼种、设备、房间、收藏和目标任务；补齐选项、存档兼容、画质档位、性能分析和桌面发行构建。

## 5. 主要技术风险

1. **水、玻璃与鱼的透明渲染**：需用原型尽早确定视觉方案，避免后期大量资产建立在不可行材质组合上。
2. **鱼类动画和游动观感**：仅让模型沿路径移动容易像“漂浮道具”；需让尾鳍摆动、转向幅度和速度相互匹配。
3. **自由摆放与遮挡**：鱼缸空间较小，造景、设备和鱼容易互相遮挡；需设计前后景、物件选择反馈和可见性规则。
4. **模拟深度**：水质变量容易不断增加。首版应坚持少量指标、明确因果和快速反馈。
5. **资源生产成本**：3D 鱼类的建模、骨骼和动画成本高于简单静态道具；先确定美术风格和单条鱼的资产规格，再扩充品种。

## 6. 引擎备选

Godot 4.7.2 为截至调研日的稳定版。官方支持导入 glTF 2.0/GLB 与 Blender 场景，并提供 AnimationTree 和 NavigationAgent3D 等工具。它可以承担本项目的 3D 原型与完整实现；鱼类水下运动同样应使用符合缸内三维空间的自定义运动逻辑。

若团队已有 Unity/C# 经验，或计划制作较多 3D 动画、材质和内容，优先 Unity 6.3 LTS。若团队更熟悉 Godot，且目标画面可由原型验证达到，则可选 Godot 4.7.2。不要只凭引擎名气决策，先用同一组原型需求评估水体画面、鱼类动画、摆放交互、性能和团队制作效率。
